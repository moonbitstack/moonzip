deflate — RFC 1951

enumBlocks

Which block types the writer may emit.

A DEFLATE stream is a run of blocks, and a block may be stored verbatim, coded with the fixed Huffman table, or coded with a table of its own. All three are ordinary DEFLATE; they differ only in size.

variants
Auto

Let the writer choose per block: it writes each candidate, measures, and keeps the smallest. This is what zlib does, and on the short bodies a response compressor sees the measurement usually lands on fixed — a dynamic block must carry its own code tables, which costs more than it saves on a few hundred bytes.

Fixed

Fixed Huffman codes only. Exactly what this library wrote before 0.4.0, for a caller whose output bytes are pinned.

Dynamic

Dynamic Huffman codes only: the writer must carry its own code tables. The largest output on text, and the reason to have it on at all.

Stored

No compression at all: the input verbatim in stored blocks. This is what level = 0 means, and asking for it by name is the way to say it without going through a level.

typeReader

Decompress a raw DEFLATE stream a piece at a time.

push takes whatever has arrived and hands back whatever it decoded; finish says no more is coming, and it is an error for the stream to be unfinished when it is called. Between calls the reader holds the input it has not got to yet and nothing else — a response body can be decompressed as it downloads, without the whole of it, or of the output, being held.

The one-shot inflate is this reader fed once and finished.

typeWriter

Compress into a DEFLATE stream a piece at a time.

The point of the streaming writer is that a body need not be held to be compressed: push takes whatever has arrived and hands back whatever is ready, and the only thing kept between calls is the last 32 KiB — the window, which is as far back as a back-reference may reach. A block is emitted every 32 KiB of input, and matches may reach back across block boundaries into the retained window, exactly as they would in a stream written in one piece.

The stream is not finished until finish is called: that is what writes the last block, and a caller who stops pushing without it has an unterminated stream.

fndeflate

pub fn deflate(BytesView, level? : Int32, window? : Int32, chain? : Int32, blocks? : Blocks) -> Bytes

Compress into a DEFLATE stream, one block over the whole input.

LZ77 finds back-references with a hash chain over the window, capped so the search stays linear in the input. blocks decides how the result is coded.

level runs 0 to 9 and means what it means in the format's reference: 0 stores the input without compressing it, 9 searches hardest, and 6 is the default every mainstream encoder uses. It sets how far back the match finder looks, with the same numbers the reference tables give it.

window is how far a back-reference may reach — 32 KiB is the most DEFLATE allows and the only value a reader can be assumed to handle. chain sets the search depth directly for a caller who would rather not go through a level.

level=0 writes stored blocks, which is what "no compression" means everywhere; blocks then has nothing to choose between.

A gzip writer that takes the body a piece at a time.

This is the shape a response compressor wants: the header goes out with the first chunk, each chunk is compressed and handed straight back, and the trailer is written when the body is declared over. Neither the body nor the compressed form is ever held whole — only the 32 KiB window the compressor needs for its back-references and the four bytes of running checksum.

typeReader

Walk an archive from the front, one member at a time.

unzip reads the central directory at the end, which is what a file on disk allows and what makes an entry addressable by name. A reader that is *receiving* an archive — from a socket, from a pipe, out of a decompressor — has no end to seek to, and the local headers are all it has. This is that reader.

It also reads what a streaming writer writes: an entry whose checksum and sizes sit in a data descriptor after its data rather than in its header. That case is why this reader feeds DEFLATE until the stream says it has ended instead of trusting a length in front of it.

typeWriter

Build an archive a member at a time.

zip is this writer with every entry added and then finished, which is the shape a caller with the whole archive in hand wants. A caller that is receiving members one at a time — a backup running, a directory being walked — wants this instead: add hands back the bytes for that member immediately, and only the central directory waits for the end.

Three knobs decide the bytes beyond the content itself:

zip64 widens the size and offset fields to sixty-four bits. It turns itself on when an entry or an offset does not fit in thirty-two, which is the only reason it exists; forcing it is for a caller whose reader expects the wider form.

descriptor puts each entry's checksum and sizes after its data instead of in its local header (APPNOTE.TXT §4.3.9). That is what a writer that streams a member it has not finished reading must do — it cannot know the sizes when it writes the header — and it costs twelve bytes a member.

password? encrypts each member with ZipCrypto, which is what the format called encryption for fifteen years. It is not a security boundary; see zipcrypt_encrypt.

fntar

pub fn tar(ArrayView[Entry]) -> Bytes

Write an archive.

Members go out in the order they are given, each as a header, its bytes padded to a block boundary, then two empty blocks to say the archive is over.

A name longer than a hundred bytes is carried in a pax extended header, which is a member of its own whose content is a list of keyword=value records. That is the POSIX answer, and it is what GNU tar and bsdtar both read; the older GNU L record is read but not written, because one way to say a thing is enough.

The archive is reproducible: the modification time comes from the entry and the owner is nobody, so the same entries always give the same bytes. Set mtime and uid on an entry when it should carry something else.

fnframe

pub fn frame(BytesView, level? : Int32) -> Bytes

Wrap LZ4 blocks in a frame: a header, the blocks, an end mark and a content checksum.

Blocks are independent, so a decoder can start at any of them; the content checksum is over the original bytes rather than the compressed ones, so it catches a decoder that produced the wrong thing rather than only a link that flipped a bit.

fnlz4

pub fn lz4(BytesView, level? : Int32) -> Bytes

Compress into the LZ4 block format.

A block is a run of sequences. Each is a token whose high nibble is how many literals follow and whose low nibble is the match length minus four, then the literals, then a two-byte back-reference, then the match length's overflow bytes. The last sequence carries literals only, and the format reserves the last five bytes of the input for them — a decoder relies on both, which is why match_start stops twelve bytes short of the end.

level picks the search depth: 0 uses one candidate per position, which is what LZ4's own "fast" mode does; higher values walk a chain. The ratio gain above the default is small and the cost is real — this is a format chosen for speed.

fnsnappy

pub fn snappy(BytesView) -> Bytes

Compress into the Snappy block format.

A block starts with the uncompressed length as a varint — the one thing a decoder is told up front, and the reason Snappy needs no bound of its own to be safe — and then a run of tags. A tag is a literal or a copy, and its two low bits say which: 00 a literal, 01 a copy with an eleven-bit offset, 10 one with a sixteen-bit offset, 11 one with a thirty-two-bit offset. The three copy forms exist so that the common cases cost two bytes.

The compressor is greedy: one candidate per position from a hash of four bytes, extended as far as it runs. Snappy's own encoder is not much cleverer, because the format's whole point is that decompression be quick.

brotli — RFC 7932

fnbrotli

pub fn brotli(BytesView, window? : Int32) -> Bytes

Brotli, RFC 7932.

The writer is deliberately a plain one: greedy LZ77 over a single hash table, one meta-block per megabyte, one block type per stream, and Huffman codes computed from the exact symbol counts. What it does **not** do is the half of brotli that earns the format its ratio: literal context modelling, block splitting, the static dictionary, and the exhaustive parse at quality 11.

That is a choice, not a gap. Those four are search problems over the same format the reader already implements, and a writer that used them would need the reference encoder's 30,000 lines to be worth the difference. This one is correct, readable by every brotli implementation, and roughly comparable to gzip on text.

window is the log of the window size, 10 to 24: how far back a copy may reach. Larger windows find more matches and cost nothing but memory while writing, since the reader keeps whatever it needs.
